# Проверка передачи и облачного просмотра 0.1.13

Реальные контрольные измерения на Android 36, 1 ноября 2026 года. Это результаты конкретного телефона, подключения и аккаунта, а не обещание одинаковой скорости у всех пользователей.

## Причина медленной отправки

Один заранее подготовленный зашифрованный контейнер — 2 100 365 байт. Шифрование исключено из таймера, архивная очередь на время сравнения приостановлена. После каждой отправки выполнены полное обратное чтение, расшифровка и сравнение паспорта оригинальных байтов.

| Сетевой клиент, путь `.bin` | От ссылки до ответа | Полная обратная проверка |
|---|---:|---|
| OkHttp, штатный режим | 17,168 с | Успешно |
| OkHttp, HTTP/1.1 | 17,138 с | Успешно |
| Android HttpsURLConnection | 17,444 с | Успешно |

Смена сетевого клиента не устранила ограничение. Затем теми же байтами и штатным клиентом проверено только влияние суффикса нового случайного имени:

| Суффикс | От ссылки до ответа | Полная обратная проверка |
|---|---:|---|
| `.bin`, перед сравнением | 17,131 с | Успешно |
| `.cv2` | 1,770 с | Успешно |
| Без расширения | 1,608 с | Успешно |
| `.bin`, после сравнения | 17,130 с | Успешно |

Таким образом, в этой проверке замедление зависит от имени объекта при выдаче ссылки на загрузку. Оно воспроизводится вне очереди и шифрования приложения. Наблюдение согласуется с [описанием ограничения по типу файла авторами YaDisk](https://yadisk.readthedocs.io/en/latest/known_issues.html). Это не официальная гарантия поведения API Яндекса. Скорость записи в локальный сетевой буфер не равна скорости доставки: для сравнения используется время до ответа сервера.

Дополнительный контроль штатного клиента: три контейнера по 8 392 061 байту с `.cv2` приняты за 2,266 / 1,867 / 1,971 секунды, включая получение ссылки. Все три прошли полную обратную проверку. Эффективная скорость — около 3,7–4,5 МБ/с на таком размере, без времени readback. Это в десятки раз быстрее прежней отправки части 8 МиБ как `.bin`, но не измерение предельной пропускной способности Wi-Fi.

Новые контейнеры оригиналов, частей видео, производных и пакетов фотофрагментов получают собственное расширение `.cv2`. Содержимое контейнера и проверки целостности не меняются. Старые объекты и неопределённые PUT сохраняют прежние адреса. У ссылок на части суффикс хранится в проверяемом манифесте; отсутствие поля означает прежний `.bin`. Независимый Python-декодер поддерживает оба варианта. Изменение расширения не добавляет защиты от чтения облаком.

## Облачное фото без местного оригинала

Использована отдельная копия тестового снимка 1440 × 3168. Она удалена из MediaStore после проверки двух облачных оригиналов и фрагментов через production LocalRelease. Пользовательские исходники сохранены.

После объединения соседних запрошенных диапазонов:

- Открытие до готовности всех видимых деталей: 5260 мс. Это не время первого грубого кадра.
- Зум до полного разрешения, sample 1: 2906 мс; получено 102 312 сетевых байт.
- Повтор того же зума: 245 мс, 0 сетевых байт.
- За сеанс получено 302 922 байта проверенных фрагментов; затронутые записи кэша после закрытия: 0.

Диапазоны объединяются только для смежных запрошенных фрагментов одного пакета. Каждый фрагмент отдельно проходит SHA-256 и AEAD до помещения в кэш. Проверки неизменности облачного объекта сохранены.

## Большое видео

Подготовлен отдельный публичный тестовый ролик 3840 × 2160, 60 кадров/с, 1 001 836 975 байт. Полный реальный цикл двух копий, восстановления, переключения качеств и очистки кэша ещё не засчитан. Частично отправленный набор не считается сохранённым и не разрешает удалять оригинал.

В ходе прежней медленной загрузки шифрование части 8 МиБ занимало примерно 50–80 мс; ожидание принятия `.bin` — примерно 65 секунд. Контроль суффиксов выше отделяет эту задержку от скорости шифрования и Wi-Fi.

### Длительная задача Android

Реальный прогон выявил отдельную остановку на `setForegroundAsync`: вложенная причина — `ForegroundServiceStartNotAllowedException`. Это запрет запуска следующей foreground-службы, а не повреждение видео и не ограничение скорости Wi-Fi.

Для явно запущенных пользователем передач на Android 14+ добавлен JobScheduler UIDT с обязательным уведомлением и прежним ограничением на сеть без тарификации. Один job использует тот же архивный движок и межпроцессную блокировку, продолжая его ограниченные проходы. Отдельный запуск службы для каждой следующей порции не нужен. Android [рекомендует UIDT для длительных пользовательских передач](https://developer.android.com/develop/background-work/background-tasks/uidt); [обычный WorkManager с foreground-службой на Android 16 также ограничен квотой job](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running).

В журнале и манифестах ничего не сбрасывается. Завершение холодной копии создаёт зависимую рабочую запись до ухода задачи в ожидание. Остановка пользователем в диспетчере задач блокирует автоматический повтор до явного продолжения; системная остановка сохраняет checkpoint. На более ранних Android остаётся путь WorkManager. Ресурсная настройка отключает UIDT-службу до API 34. Это не обещание неограниченной фоновой работы: условия сети и остановки Android остаются обязательными.

Счётчики частей обновляются по сохранённой ревизии, включая этапы, на которых общий статус ещё `QUEUED`. Уведомление открывает галерею; при общей ошибке очереди есть отдельная кнопка «Продолжить передачу».

Когда местный оригинал ещё доступен, рабочая multipart-копия может создаваться из него: привязка MediaStore проверяется до/после чтения, свежий полный SHA-256, длина и даты сравниваются с уже проверенным холодным оригиналом. Каждая новая часть также сверяется с плановым хешем и читается обратно после отправки. Если подходящего местного источника нет, используется прежнее чтение холодного архива. Это устраняет повторное скачивание целого видео при первоначальном сохранении двух копий.

Между завершёнными шагами одного приоритета очередь передаёт ход следующему файлу. Курсор сохраняется отдельно от доказательств сохранности; чтение статуса его не меняет. Уточнение неопределённого PUT и подготовленного объекта сохраняет приоритет. Большой `QUEUED` multipart-файл больше не задерживает все новые фотографии до окончания видео.

Технические идентификаторы устройства, аккаунт, OAuth и содержимое личных снимков в публичный отчёт не включены. Сырые отчёты остаются в игнорируемом каталоге `artifacts`.

## Проверки кода

- `gradlew test :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug`: успешно. JVM-отчёты содержат 170 тестов, 0 ошибок/падений, 3 пропуска.
- Multipart-регрессии включают потерянный ответ PUT, совместное восстановление старых `.bin` и новых `.cv2`, оба суффикса корня и независимую сборку Python без исходного файла. Legacy-ссылки не получают дополнительного поля при каноническом кодировании.
- На телефоне отдельно пройдена проверка сохранения старых путей пакетов фрагментов и сериализации новых путей; неизвестные суффиксы отклоняются.
- На отдельном API 35 эмуляторе: 75 объявленных Android-тестов, 68 выполнены успешно, 7 opt-in проверок пропущены, 0 падений. Доступ к пользовательскому облаку в этот прогон не входит. Дополнительно пройдены три проверки жизненного цикла и ограничений UIDT, включая добавление работы на границе завершения и остановленную задачу.
- Три сравнения сетевых клиентов, четыре варианта имени и три больших контрольных контейнера проверены на реальном Яндекс Диске. Это отдельные opt-in испытания, публичная CI не использует пользовательскую сессию.

# Проверка 0.1.5 — точные оригиналы и исходные даты

9 октября 2026. В Android добавлено сохранение наблюдавшихся исходных дат в CVPOS3 и их перенос из проверенного Cold Archive в независимый Gallery Store. Байты фото не пересжимаются и не переписываются. Старые CVPOS2 и POS v1 читаются; старые облачные задачи сохраняют адреса и формат уже подготовленного контейнера.

## Что сохраняется и восстанавливается

- Полный исходный файл, включая EXIF/XMP/ICC/GPS, MakerNotes, встроенные даты и неизвестные приложению данные. Проверяется полное равенство байтов и SHA-256, а не сходство картинки, размеров или качества.
- Дата изменения с фактически открытого оригинального дескриптора: Unix seconds + nanos. Она проверяется между чтениями источника и не заменяется временем шифрования/загрузки/скачивания.
- Доступные DATE_ADDED и DATE_TAKEN из MediaStore сохраняются как наблюдения индекса. Достоверная дата создания имеет отдельное nullable-поле. Linux ctime и дата добавления не выдаются за создание; в текущем Android-пути birth time неизвестен.
- После полного восстановления и повторного чтения назначения приложение пытается установить исходную mtime и сравнивает её нативным stat. Невозможность установки или потеря точности сообщаются отдельно; корректные восстановленные байты остаются доступны.

Android может назначить новую дату создания файла и новую дату добавления записи в MediaStore. Через произвольный SAF-провайдер нельзя универсально вернуть эти системные поля. Поэтому сохранение всех дат операционной системы не заявляется. Встроенные даты исходного медиа при этом остаются точными. См. [CVPOS3](CVPOS3_SPEC.md) и [описание полей MediaStore](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns).

Новые пять полей дат находятся в открытом заголовке, как исходное имя и MIME. По выбранной пользователем политике ключ восстановления находится в контейнере. Провайдер технически может восстановить оригинал; это не конфиденциальность от облака. Новые файлы требуют обновлённого офлайн-декодера 0.1.5.

## Десять загруженных фотографий

Взяты десять настоящих JPEG/EXIF-примеров из публичного [ianare/exif-samples](https://github.com/ianare/exif-samples), commit `5332a9cf0220e9c6c93f88a187daa90808051e10`. Это небольшие тестовые изображения, а не выборка полноразмерных современных форматов. [Манифест](fixtures/ten-photo-corpus.json) содержит точные URL, размеры и SHA-256; upstream указывает CC BY-SA 4.0 для предоставленных пользователями изображений. Файлы скачиваются в игнорируемые test assets и в Git не включены.

Android-проверка выполнена на отдельном API 35 эмуляторе. Использовано файловое хранилище, моделирующее облако, с тем же ArchiveCloud-контрактом и Android-путём упаковки/восстановления. Это не проверка серверов Яндекса.

Для каждого из десяти файлов:

1. Создан отдельный оригинал в приватном тестовом каталоге. Для измеримого теста ему назначена известная mtime с долями секунды `123456000` nanos; EXIF не изменяется.
2. Выполнены упаковка, загрузка и полное обратное чтение холодного контейнера до VERIFIED. Проверено, что упаковка не изменила дату источника.
3. Удалён только этот созданный тестом локальный оригинал, проверено его отсутствие.
4. Из прочитанного холодного контейнера создана отдельная рабочая копия Gallery Store с теми же байтами и датами, новым bundle ID и другим физическим контейнером.
5. Холодная и рабочая копии скачаны и восстановлены независимо. Для обеих совпали все байты, исходный SHA-256, EXIF-поля даты/камеры/GPS и точная нативная mtime.

Результат: **10 из 10 фотографий, 20 из 20 восстановленных файлов**. Отчёт конкретного запуска: локальный `artifacts/roundtrip-ten-photos.csv`, десять строк PASS. Пользовательская медиатека телефона не использовалась и не удалялась.

## Остальные проверки и телефон

- 72 JVM-теста прошли: в том числе CVPOS3 roundtrip, защита даты заголовка от изменения, чтение старого CVPOS2, неизвестные даты, некорректная числовая запись, Kotlin → независимый Python и Python → Kotlin.
- Android instrumentation: 18 проверок прошли, 1 пропущена через assumption, 0 ошибок. В пропущенной проверке нужен реальный аккаунт Яндекса; на тестовом эмуляторе его нет. Общий runner выводит `OK (19 tests)`.
- Отдельные JVM/Python-декодеры восстановили CVPOS3 fixture на 65537 байт вне Android; SHA-256 и mtime `1700000000123456700` ns совпали. Все пять записанных наблюдений дат доступны после восстановления.
- APK собран. Android lint: 0 ошибок, 22 предупреждения; проверки не отключены.
- Основной APK 0.1.5 установлен обновлением на подключённый телефон Android API 36; версия 6/0.1.5 и успешный запуск MainActivity подтверждены. Использован прежний зарегистрированный OAuth-сертификат.
- Телефон отклонил установку отдельного тестового APK с `Failure [-99]`. Поэтому автоматический тест десяти фотографий на реальном Яндекс Диске не запускался. Результат не считается успешным облачным тестом; причина отказа ОС не установлена. Ограничения устройства не обходились.

Реальная Yandex-проверка подготовлена в `TenPhotoRoundtripAndroidTest.tenPhotographsOnRealYandexWhenAccountHasBeenConnected`. Она использует только эти публичные фотографии, отдельные случайные облачные имена и приватные исходники текущего запуска. Она не удаляет личные файлы или облачные оригиналы. Проверенные тестовые объекты остаются в облаке.

## Воспроизведение и артефакты

На Windows подготовить corpus перед сборкой тестового APK:

```powershell
./scripts/prepare-photo-corpus.ps1
./gradlew.bat test :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug :pos-reference-decoder:installDist
./scripts/package-recovery.ps1
```

Нужны JDK/Android SDK и независимая Python-зависимость из `requirements-recovery.txt`; настройки интерпретатора описаны в README. Тестовый APK и основной APK устанавливаются только на выделенный тестовый эмулятор, затем запускается AndroidJUnitRunner. Выбор только реального метода на устройстве допустим после успешной установки тестового APK и подключения аккаунта.

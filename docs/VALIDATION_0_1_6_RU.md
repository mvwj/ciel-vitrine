# Проверка 0.1.6 — лента по дням и Яндекс Диск

9–10 октября 2026. Основной APK 0.1.6 установлен обновлением на телефон Android API 36. Подпись и Client ID прежние; сохранённый вход в Яндекс остаётся на устройстве.

## Лента

Фотографии и видео расположены по дням съёмки, от новых к старым. Сначала используется DATE_TAKEN в миллисекундах; если его нет — время изменения, затем время добавления в секундах. Отображение дней использует текущий часовой пояс устройства. Никакие исходные медиа-байты или даты файлов при этом не меняются.

Внутри дня — три столбца квадратных миниатюр без закруглений, внешних полей и промежутков между ячейками/рядами. Между днями находится подпись с отступами. Фото и видео открываются прежним просмотрщиком.

Справа при наличии прокрутки показан ползунок. Его перетаскивание переходит по всей доступной ленте, показывает дату у ручки и вызывает системный haptic feedback при переходе в другой день. Вибрация учитывает настройки устройства. Для доступности предусмотрено действие изменения позиции; при обычной прокрутке дата также показывается возле ручки.

Для перехода к старому дню нужен полный индекс доступных метаданных. MediaStore читается в фоновом потоке, повторяющиеся строки разделяются, отмена проверяется между записями. Список больше не ограничен первыми 240 файлами. Исходные файлы и миниатюры не загружаются всей библиотекой: lazy grid создаёт видимые ячейки. При изменении разрешений прежние недоступные записи сразу скрываются. Незавершённые и находящиеся в системной корзине записи исключены.

Индекс метаданных пока целиком находится в памяти. Для сотен тысяч файлов ещё требуются измерения памяти/задержек и каталог с выборкой диапазонов. Эти изменения не являются подтверждением производительности на таких библиотеках. Для облачных задач сохраняется отдельный транзакционный постраничный inventory.

## Проверки

- 77 JVM-тестов прошли, 0 ошибок. Добавлены проверки успешного повторного чтения метаданных после обрыва, остановки после двух неудачных GET и отсутствия повторного PUT в этом механизме. Проверены относительные и межсерверные перенаправления скачивания, отсутствие передачи OAuth на другой хост, а также отказ до вызова декодера при внешнем адресе, HTTP и цикле.
- На отдельном API 35 эмуляторе: 21 Android-проверка прошла, 1 реальная Yandex-проверка пропущена из-за отсутствия аккаунта, 0 ошибок. Последний запуск с исправленным провайдером: `OK (22 tests)`, 55.197 s.
- Новые Compose-проверки измеряют квадратность и соприкосновение соседних ячеек/рядов, проверяют подпись и промежуток между днями. Перетаскивание на ленте из 300 фотографий показывает дату и вызывает haptic API; переходы достигают самого старого и самого нового дня. Проверены единицы и приоритет исходных дат.
- APK и тестовый APK собраны, lint: 0 ошибок, 25 предупреждений. Проверки не отключены.
- На телефоне подтверждены versionCode=7/versionName=0.1.6 и успешный запуск MainActivity. Внешний вид дополнительно просмотрен на скриншоте эмулятора с тестовой медиатекой.
- Независимые Python-декодеры повторно проверили четыре POS v1 и десять CVPOS2-фикстур, все байты совпали. Формат CVPOS3 в этом обновлении не менялся; независимые проверки его байтов и mtime описаны в [0.1.5](VALIDATION_0_1_5_RU.md).

## Яндекс

Регистрация уже существовала. После включения доступа «Информация о Диске» и повторного входа пользователь подтвердил статус «Яндекс Диск подключён». Отдельный тестовый APK теперь успешно устанавливается. Client Secret не нужен Android LoginSDK и не добавлен в исходники/сборку; токен остаётся в защищённом хранилище приложения.

Первая реальная попытка на 0.1.5 прервалась по сетевому тайм-ауту на предварительном GET сведений о будущем холодном объекте, до отправки файла. VERIFIED не выдан. В 0.1.6 запросы небольших метаданных имеют deadline 75 s и один явный повтор после IOException; закрываются неиспользуемые соединения. Повтор покрывает чтение тела ответа. PUT и callback скачивания, который мог уже записать данные, этим механизмом не повторяются.

Следующая попытка на 0.1.6 прошла подготовку/отправку и дошла до проверки первой холодной копии, но ОС телефона завершила процесс: ApplicationExitInfo reason=13, `Cached(nirvana)[(instrumentation)]`. Это не считается успешным тестом восстановления и не является подтверждением дефекта криптоформата.

Реальная проверка теперь открывает MainActivity и временно удерживает экран включённым во время теста; постоянные системные настройки не меняются. Есть безопасные сообщения о шагах account/metadata/upload/download без токенов и временных URL. Тест использует только десять публичных JPEG из [манифеста](fixtures/ten-photo-corpus.json), приватные исходники текущего запуска и отдельные случайные облачные имена. Личные фото не удаляет. Проверенные тестовые облачные объекты оставляет в аккаунте.

Запуск с активной галереей выявил HTTP 302 при скачивании. Клиент прежде запрещал все перенаправления. Теперь он вручную проходит до пяти переходов, каждый раз проверяя HTTPS, порт 443, отсутствие URL-учётных данных и домен Яндекса; отклоняет цикл и неизвестный адрес. OAuth передаётся на начальный download URL, как требует [документация Яндекса](https://yandex.com/dev/disk-api/doc/en/reference/content), и убирается при смене хоста. Callback полного чтения вызывается только на конечном HTTP 200 и не повторяется после частичного чтения. Допуск автоматических перенаправлений HTTP-клиента выключен.

Последняя попытка 9 октября после исправления перенаправлений дошла до VERIFIED первой холодной копии, но журнал оборвался при потере управляющего процесса на компьютере; итогового статуса и десяти результатов нет. Этот запуск не засчитан. Оставшаяся instrumentation была остановлена перед новым запуском 10 октября.

**10 октября полная реальная проверка прошла:** `OK (1 test)`, 309.672 s, без пропуска или ошибки. Все десять публичных JPEG (суммарно 123694 исходных байта) прошли Cold Archive → VERIFIED → удаление только приватного исходника → независимый Gallery Store → VERIFIED. После этого скачаны и восстановлены обе копии каждого фото: **20 восстановлений**. Сравнение каждого файла проверяет все исходные байты; дополнительно сравниваются семь полей EXIF, в том числе даты и GPS. Нативный `Os.stat` подтвердил исходную mtime, включая `123456000` наносекунд, для каждой восстановленной копии. Упаковка не изменила mtime тестового исходника. До удаления исходника проверены длина/SHA-256 оригинала и всего контейнера, bundle ID и стабильность облачных object ID/версии.

В выгруженном CSV десять строк PASS. Их имена, размеры и SHA-256 отдельно сверены с закреплённым манифестом исходных JPEG. [Таблица результатов](fixtures/real-yandex-0.1.6.csv) содержит только данные публичных тестовых файлов; UID, токены и адреса облачных объектов в неё не включены. Полный локальный CSV с адресами собственных тестовых контейнеров находится в `artifacts/roundtrip-real-yandex-0.1.6.csv`. В аккаунте остались двадцать проверенных контейнеров этого запуска и возможные тестовые объекты ранних незавершённых попыток. Облачное удаление не выполнялось.

Это проверка небольших JPEG на конкретном телефоне и аккаунте; она не подтверждает все форматы, большие видео, производительность массовой загрузки или восстановление при любых внешних сбоях. Длительность включает дополнительные полные чтения и обе независимые проверки восстановления, а не только отправку файлов. После теста обычная MainActivity запущена снова; временный флаг удержания экрана относится только к закрытой тестовой Activity.

Для воспроизведения на личном телефоне запускается только метод `com.cielvitrine.app.TenPhotoRoundtripAndroidTest#tenPhotographsOnRealYandexWhenAccountHasBeenConnected` через AndroidJUnitRunner. Полный набор permission/inventory/session-тестов используется исключительно на отдельном тестовом эмуляторе: он меняет разрешения и тестовые ключи/сессии.
